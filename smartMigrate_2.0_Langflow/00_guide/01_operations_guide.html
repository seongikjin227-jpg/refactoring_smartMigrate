SmartMigrate 운영 가이드

설치와 최초 등록은 시작 가이드를 따르세요. 이 문서는 등록된 작업의 조회·실행·보정에 사용하세요.

1. 작업 조회와 실행

Migration은 MAP_ID, SQL 작업은 SQL_SEQ로 지정하세요. SQL_SEQ를 모르면 SQL_ID와 SPACE_NM을 함께 적으세요. 이전 대상을 “그 작업”, “네”만으로 지정하지 마세요.

목적요청 예시
전체 현황대시보드 보여줘.
현재 실행지금 실행 중인 작업을 보여줘.
최근 결과최근 SQL Conversion 결과와 실패 원인을 보여줘.
Migration 조회MAP_ID 101의 상태와 최근 실패 로그를 보여줘.
SQL 조회SQL_SEQ 42의 Conversion 상태와 TO_SQL 원문을 보여줘.
특정 실행MAP_ID 101의 DB Migration을 실행해줘.
특정 SQL 실행SQL_SEQ 42의 SQL Conversion을 실행해줘.
전체 실행전체 workflow의 남은 작업을 실행해줘.
실패 재시도 준비MAP_ID 101의 실패 상태는 유지하고 RETRY_COUNT를 0으로 바꿔줘.

재시도 준비·SQL 저장과 실행은 별도 요청입니다. 변경 결과를 확인한 뒤 실행하세요.

2. 실행 후보와 선행 조건

도메인자동 실행 후보
DB MigrationUSE_YN=Y, STATUS가 NULL 또는 FAIL-*, RETRY_COUNT < 2
SQL ConversionSTATUS_CONVERSION이 NULL 또는 FAIL-*, RETRY_COUNT < 2
SQL TuningConversion PASS, STATUS_TUNING이 NULL 또는 FAIL-*, RETRY_COUNT < 2
SQL FormattingTuning PASS, FORMATTED_SQL이 비어 있음

RUNNING 상태는 자동 후보가 아닙니다. SQL 작업에는 USE_YN 필터를 적용하지 않습니다.

단독 Conversion은 사용 대상 Migration이 완료되어야 하며, 단독 Tuning은 Migration과 Conversion 선행 조건을 충족해야 합니다. 전체 workflow는 Migration부터 진행하고, SQL 단계 진입 전에 Migration 완료 상태를 다시 확인합니다.

3. 실패 상태별 재개

재개 위치는 USER_EDITED 표시가 아니라 DB 상태로 결정됩니다.

도메인상태다음 실행 시작점
MigrationFAIL-TRUNCATE / FAIL-INSERTMIG_SQL 생성·이관 단계
MigrationFAIL-TESTVERIFY_SQL 생성·건수 검증. INSERT 재실행 안 함
MigrationFAIL-TEST2레코드 검증
MigrationPASS완료
ConversionFAIL-TOBETO_SQL 생성
ConversionFAIL-BIND저장한 TO_SQL로 bind 생성
ConversionFAIL-TEST저장한 SQL·bind로 test 생성·실행
ConversionPASS-CONVERSION완료, Tuning 대상
TuningFAIL-TUNEDTUNED_TO_SQL 생성
TuningFAIL-TEST저장한 TUNED_TO_SQL로 검증
TuningPASS-TUNING완료, Formatting 대상

Conversion 재개에 필요한 이전 SQL이 없으면 상태를 이전 단계로 되돌리지 않고 실패 상태를 유지합니다. 이 경우 필요한 SQL을 올바른 종류로 저장하세요. Formatting은 현재 실행이 전달한 생성 SQL을 대상으로 하며 대상이 없으면 NO_FORMATTING_TARGETS로 통과합니다.

저장 뒤 동기화와 유사 후보 처리

Migration은 저장한 MIG_SQL/VERIFY_SQL 한 종류를 Milvus에 동기화합니다. Migration에는 유사 후보 자동 REF_SEQ 적용 기능이 없습니다.

Conversion Correct SQL 저장 후 Management Agent는 해당 종류를 동기화하고 AS-IS 유사 실패 SQL을 검색합니다. 유사도가 80%를 초과하고 후보의 실패 단계가 아래 조건과 일치할 때 REF_SEQ와 RETRY_COUNT=0을 자동 반영합니다.

저장한 Correct SQL 종류참고할 수 있는 후보 상태
TO_SQLFAIL-TOBE
BIND_SQLFAIL-BIND
TEST_SQLFAIL-TEST

후보의 실패 상태는 유지하고 SQL 전문을 복사하거나 즉시 실행하지 않습니다. 응답에서 저장·동기화·검색·REF_SEQ 반영 결과를 각각 확인하세요.

5. 유사 SQL 검색과 참고 대상 지정

SQL_SEQ 42와 AS-IS SQL이 유사한 실패 Conversion 작업을 찾아줘.

단독 유사 검색은 조회만 수행합니다. 기본 최소 유사도는 70%이며 필요하면 요청에 기준을 적으세요. 후보의 SQL_SEQ·실패 단계·테이블·유사도를 확인하세요.

SQL_SEQ 57의 참고 Correct SQL을 REF_SEQ 42로 지정해줘.

참고 작업은 Correct SQL 컬렉션에 있어야 합니다. 지정한 뒤 별도로 실행하면 해당 실패 단계에서 힌트로 사용합니다.

6. RAG 규칙과 검색 자료 갱신

규칙입력
Conversion GENERALCATEGORY=SQL_CONVERSION, SOURCE_TABLES, GUIDANCE_TEXT
Conversion SEARCHCATEGORY=SQL_CONVERSION, SOURCE_TABLES, SOURCE_SQL, TARGET_SQL
Tuning GENERALCATEGORY=SQL_TUNING, GUIDANCE_TEXT
Tuning SEARCHCATEGORY=SQL_TUNING, GUIDANCE_TEXT, SOURCE_SQL, TARGET_SQL

SQL Tuning GENERAL 가이드를 등록해줘. GUIDANCE_TEXT=[실제 프로젝트 규칙]

RAG_ID 25의 규칙을 비활성화해줘.

RAG 비활성화는 먼저 Oracle의 USE_YN=N을 저장합니다. 이어서 아래 동기화를 요청하면 Milvus의 해당 문서도 비활성화되어 검색에서 제외됩니다. Milvus를 직접 수정할 필요는 없습니다.

RAG Guide와 AS-IS SQL을 Milvus에 전체 동기화해줘.

RAG 변경 후에는 동기화를 별도로 요청하세요. sync_all은 RAG·AS-IS SQL 동기화와 없는 컬렉션 생성에 사용하며 Correct SQL 전체를 일괄 적재하지 않습니다. 최초 생성 절차는 시작 가이드의 Milvus 단계를 따르세요.

저장된 Correct SQL의 동기화만 다시 요청할 수도 있습니다. 이 요청은 상태·REF_SEQ·재시도 횟수를 변경하거나 작업을 실행하지 않습니다.

SQL_SEQ 101의 저장된 Correct TO_SQL만 Milvus에 동기화해줘.

7. 결과 확인과 오류 복구

Migration은 최종 상태·실행 결과와 저장된 MIG_SQL·VERIFY_SQL을 확인하세요.

Conversion은 TO_SQL·BIND_SQL·BIND_SET·TEST_SQL과 PASS-CONVERSION을 확인하세요. Tuning은 TUNED_TO_SQL·TUNED_RESULT·PASS-TUNING을, Formatting은 FORMATTED_SQL을 확인하세요.

상황조치
최근 결과와 전체 건수가 다름최근 갱신 작업 목록과 전체 상태 집계를 구분하고 실행 시각·대상을 지정
오류 응답을 받음오류를 0건으로 해석하지 말고 대상 상태·로그를 다시 조회
SQL 원문이 잘림대상 번호·컬럼을 지정해 “전체 원문” 요청
Correct SQL 저장 뒤 실행되지 않음저장된 상태 확인 후 별도 실행 요청
동기화만 실패함저장을 반복하지 말고 해당 자료의 동기화부터 재시도
매핑이 반영되지 않음execute_updates 옵션과 성공·실패·미반영 통계 확인
선행 조건으로 막힘선행 작업의 상태·오류 확인 후 해결
로그·연결 오류가 반복됨요청 시각·도메인·식별자를 전달하고 새 계정·권한·노드 연결 점검

매핑 정의서 다운로드·업로드는 시작 가이드의 고정 요청문을 그대로 사용하세요.
