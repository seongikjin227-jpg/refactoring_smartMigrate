# Langflow Workflow Logging Rules

## 0. 현재 결론

첨부 PDF는 Langflow 환경에서 `self.log()`, `lfx.log.logger`, Python `logging`, handler 방식을 테스트한 참고 자료다. 최종 적용은 현재 `smartMigrate_2.0_Langflow` 코드 구조를 기준으로 한다.

현재 결론은 다음과 같다.

- Root Logger는 사용하지 않는다.
- SmartMigrate workflow 로그는 `logging.getLogger("smartmigrate.workflow")` 전용 logger만 사용한다.
- `00A Log Runtime Start`에서 `SmartMigrateDBHandler`를 등록한다.
- `SmartMigrateDBHandler`는 workflow 시작 시 DB connection을 한 번 만들고 보유한다.
- 각 컴포넌트의 `logger.info/error(...)` 호출마다 handler가 같은 connection으로 지정한 `system_schema.NEXT_MIG_LOG`에 즉시 insert한다.
- 이전 방식이었던 batch read/save/Result Table 역할은 제거한다.
- 별도 종료 logging 컴포넌트는 두지 않는다.
- 다음 workflow 시작 시 `00A`가 기존 handler를 제거하고 `handler.close()`를 호출해 이전 DB connection을 닫는다.

## 1. 목적

목적은 Langflow에서 어떤 컴포넌트가 어떤 순서로 실행됐는지 DB에서 확인하는 것이다.

이 runtime logging은 기존 업무 감사 로그를 대체하지 않는다.

- 컴포넌트 이동, 함수 실행, loop item, sleep 전후 확인: `smartmigrate.workflow` logger -> `SmartMigrateDBHandler` -> `NEXT_MIG_LOG`
- SQL 생성/실행/검증/재시도/실패 이력: 기존 `10C` 업무 로그 유지
- SQL 변환/튜닝/포맷팅 상세 이력: `12C`/`15C`/`17C`도 `smartmigrate.workflow` logger -> `SmartMigrateDBHandler` -> `NEXT_MIG_LOG`로 기록

## 2. Logger 기준

SmartMigrate workflow logging은 전용 logger만 사용한다.

```python
LOGGER_NAME = "smartmigrate.workflow"
logger = logging.getLogger(LOGGER_NAME)
logger.propagate = False
```

아래 Root Logger 패턴은 SmartMigrate workflow logging 수집 용도로 사용하지 않는다.

```python
logging.getLogger()
root_logger = logging.getLogger()
root_logger.addHandler(...)
logging.getLogger().handlers
```

Root Logger에 handler를 붙이면 Langflow 내부 로그(`lfx.custom.validate` 등)까지 섞일 수 있으므로 금지한다.

## 3. 00A Log Runtime Start

`00A_logRuntimeStart.py`는 workflow 시작 시 다음 순서로 처리한다.

1. `logging.getLogger("smartmigrate.workflow")` 획득
2. 해당 logger에 등록된 기존 handler 제거
3. 제거한 handler는 `close()`
4. logger level을 `logging.DEBUG`로 설정
5. `logger.propagate = False`
6. 새 `SmartMigrateDBHandler` 생성
7. DB config는 여기서만 전달
8. logger에 handler 등록
9. workflow start 로그를 즉시 DB insert
10. 입력 payload를 그대로 다음 컴포넌트로 전달

Handler marker는 아래 값으로 고정한다.

```python
HANDLER_MARKER = "SmartMigrateHandler"
```

Handler 검색은 `isinstance()`나 `id(handler)`가 아니라 marker attribute 기준으로 한다.

```python
getattr(handler, "handler_marker", None) == "SmartMigrateHandler"
```

Langflow Custom Component가 reload/recompile되면 같은 클래스명이어도 Python class object가 달라질 수 있으므로 `isinstance()`를 검색 기준으로 쓰지 않는다.

## 4. SmartMigrateDBHandler

`SmartMigrateDBHandler`는 생성 시점에 DB connection을 한 번 만든다.

```python
class SmartMigrateDBHandler(logging.Handler):
    def __init__(self, db_config):
        super().__init__(logging.DEBUG)
        self.handler_marker = "SmartMigrateHandler"
        self.connection = create_db_connection(db_config)
```

`emit()`마다 새 connection을 만들지 않는다. `emit()`에서는 `workflow_log`와 `record.getMessage()`를 읽어 기존 로그 테이블에 insert한다. cursor는 insert 시점마다 생성하고 닫는다.

## 5. Component Logging 형식

각 컴포넌트는 handler를 만들지 않는다. DB connection/input/insert helper도 갖지 않는다.

컴포넌트에서는 전용 logger만 호출한다.

```python
logging.getLogger("smartmigrate.workflow").info("before build_result", extra={"workflow_log": [0, "WORKFLOW", "18D_FULL_WORKFLOW_DASHBOARD", "INFO", "BUILD_RESULT", "START", 0]})
```

`workflow_log` list 순서는 다음과 같다.

```text
map_id, mig_kind, log_type, log_level, step_name, status, retry_count, generate_sql
```

`MESSAGE` 컬럼에는 `logger.info(...)` 또는 `logger.error(...)`의 첫 번째 메시지를 사용한다. 같은 메시지를 `workflow_log` list 안에 중복해서 쓰지 않는다.

`generate_sql`은 선택값이다. 일반 workflow 이동 로그는 7개 값만 넣으면 `GENERATE_SQL` 컬럼에 `NULL`이 들어간다. 최종 LLM 프롬프트, 생성 SQL, 검증 SQL처럼 본문을 남겨야 하는 경우에만 8번째 값으로 넣는다.

## 6. NEXT_MIG_LOG 기준

Runtime workflow log insert 대상 컬럼은 다음이다.

```text
LOG_ID
MAP_ID
MIG_KIND
LOG_TYPE
LOG_LEVEL
STEP_NAME
STATUS
MESSAGE
RETRY_COUNT
GENERATE_SQL
CREATED_AT
```

`LOG_ID`는 `MIGRATION_LOG_SEQ.NEXTVAL`을 사용한다.

`UPD_TS`는 사용하지 않는다. Langflow 테스트 DB 기준 `NEXT_MIG_LOG`에는 `CREATED_AT`은 있고 `UPD_TS`는 없다.

일반 runtime workflow log에서는 `GENERATE_SQL`을 비워 둔다. 생성 SQL, 검증 SQL, 변환 SQL, 튜닝 SQL, 포맷팅 SQL처럼 본문이 필요한 업무 로그는 logging 호출의 8번째 값으로 전달해서 `GENERATE_SQL`에 기록한다.

`10C_migOneJobPocExecutor`의 업무 로그는 `MIG_KIND = DB_MIGRATION`으로 기록한다. LLM 호출 직전에 최종 프롬프트 조합 결과를 logging으로 남기며, `LOG_TYPE = PROMPT_BUILD`, `STEP_NAME = PROMPT_BUILD`를 사용한다. 프롬프트 전문은 `workflow_log`의 8번째 값으로 전달해서 `GENERATE_SQL` CLOB 컬럼에 저장한다.

`12C`/`15C`/`17C`의 SQL pipeline 로그도 `NEXT_SQL_LOG`를 사용하지 않고 `NEXT_MIG_LOG`에 기록한다. 이때 `MIG_KIND`는 각각 `SQL_CONVERSION`, `SQL_TUNING`, `SQL_FORMATTING`을 사용하고, 기존 `SPACE_NM`과 `SQL_ID`는 `MAP_ID`에 `sql_id / space_nm` 형식으로 합쳐서 저장한다. SQL 본문은 `GENERATE_SQL` 컬럼에 저장한다.

`11B_failureCauseAnalyzer`는 `NEXT_MIG_LOG` 조회 시 `MIG_KIND`로 도메인을 분리한다. DB Migration 실패 로그는 `MIG_KIND = DB_MIGRATION`만 조회하고, SQL 계열 실패 로그는 `MIG_KIND IN (SQL_CONVERSION, SQL_TUNING, SQL_FORMATTING)`만 조회한다. DB Migration 쪽 조회 결과에 SQL Conversion/Tuning/Formatting 로그가 섞이면 안 된다.

## 7. Handler 정리

별도 종료 컴포넌트는 두지 않는다. 다음 workflow 시작 시 `00A_logRuntimeStart.py`가 전용 logger의 기존 handler를 제거하고 `handler.close()`를 호출한다.

```python
logger = logging.getLogger("smartmigrate.workflow")
for handler in list(logger.handlers):
    if getattr(handler, "handler_marker", None) == "SmartMigrateHandler":
        logger.removeHandler(handler)
        handler.close()
```

`handler.close()` 안에서 보유 중인 DB connection도 닫는다. 단일 사용자 테스트 기준에서는 다음 실행 시작 시 이전 connection이 정리되는 방식으로 둔다.

## 8. 기존 업무 로그 유지

아래 코드는 runtime workflow 순서 로그가 아니라 업무 감사 로그이므로 유지한다.

| 컴포넌트 | 기존 기록 대상 | 유지 이유 |
|---|---|---|
| `10C_migOneJobPocExecutor` | `NEXT_MIG_LOG` | migration 단계, retry, 생성/실행 SQL, 실패 이력 |
| `12C_sqlConversionOneJobPocExecutor` | `NEXT_MIG_LOG` | SQL 변환 결과와 단계 메타데이터 |
| `15C_sqlTuningOneJobPocExecutor` | `NEXT_MIG_LOG` | SQL 튜닝 결과와 단계 메타데이터 |
| `17C_sqlFormattingOneJobPocExecutor` | `NEXT_MIG_LOG` | SQL 포맷팅 결과와 단계 메타데이터 |

## 9. 확인 쿼리

```sql
SELECT LOG_ID,
       CREATED_AT,
       MAP_ID,
       MIG_KIND,
       LOG_TYPE,
       LOG_LEVEL,
       STEP_NAME,
       STATUS,
       MESSAGE,
       RETRY_COUNT
  FROM NEXT_MIG_LOG
 WHERE MAP_ID = 0
 ORDER BY LOG_ID;
```

## 2026-10-07 입력/매핑 로그

00A는 원본 Message를 CHAT_INPUT의 GENERATE_SQL CLOB에 기록하고 workbook URL이 있으면 00A_ATTACHMENT_PARSE에 parsed_excel 또는 오류를 남긴다. 원본 Message text와 metadata를 보존한다. 02는 02_INPUT_MESSAGE, 02_FINAL_OUTPUT에 전달 payload를 기록한다.
02 라우팅 호출 로그 순서는 02_INTENT_ROUTER / START → 02_LLM_ROUTE_PROMPT / START → 02_LLM_ROUTE_RESPONSE / PASS이다. 02_LLM_ROUTE_PROMPT의 GENERATE_SQL CLOB에는 실제 llm.invoke에 전달한 System/User 메시지의 role/content 전체를 JSON 배열로 저장한다. 기존 입력 진단 로그도 유지한다.
04 전달 직전에는 02_TO_04_PAYLOAD / SEND_04 / PASS를 기록한다. GENERATE_SQL CLOB에는 component, selected_output, next_node, history와 첨부 metadata를 포함한 실제 Management Data 출력 JSON 전체를 저장한다. 02_FINAL_OUTPUT은 branch 정보 추가 전 공통 payload이며, 04 입력을 대조할 때는 02_TO_04_PAYLOAD를 확인한다.
매핑 전용 생성기는 LOG_TYPE=04_MAPPING_RULE과 STEP_NAME=LOAD_PK:SELECT / GENERATE_SQL:LLM / EXECUTE_SQL:STATEMENT / COMPLETE:TRANSACTION / ROLLBACK:TRANSACTION을 사용한다. SQL 실행 로그 PASS는 문장 성공이며 최종 commit 성공은 COMPLETE:TRANSACTION으로 확인한다. handler는 LOG_TYPE 20자, STEP_NAME 50자, MESSAGE 4000자로 제한하고 상세 원문은 GENERATE_SQL CLOB에 저장한다.

## 2026-10-08 작업 조회/라우팅 로그

06 로그 순서: 06_INPUT_PAYLOAD → 06_TARGET_FILTER → 06_DB_QUERY → 06_QUERY_RESULT → 06_FINAL_OUTPUT.
06_TARGET_FILTER에는 02 입력 필터와 검증한 필터, 원문, exact target 유무를 기록한다. 06은 원문에서 식별자를 추출하지 않는다. 06_DB_QUERY에는 실제 SELECT와 bind 값을 기록하며, 06_QUERY_RESULT에는 전체 카운트, requested_jobs, requested_target_status(상태·USE_YN·RETRY_COUNT 등), 대상 조회 실행 여부를 기록한다. 06_FINAL_OUTPUT은 실제 08 전달 payload다. should_execute=false 또는 clarification_required=true인 경우 조회 없이 SKIP 출력 로그를 남긴다.

02_LLM_ROUTE_PROMPT는 실제 의도·대상 추출 LLM의 System/User 메시지, 02_LLM_ROUTE_RESPONSE는 파싱 전 응답이다. 02_TO_06_PAYLOAD는 branch 정보가 포함된 실제 06 전달 JSON이며 06_INPUT_PAYLOAD와 대조한다.

08 로그 순서: 08_INPUT_PAYLOAD → 08_ROUTE_INPUT → 08_FINAL_OUTPUT → 08_TO_NEXT_PAYLOAD 또는 08_MESSAGE_OUTPUT.
08_INPUT_PAYLOAD는 06 수신 payload다. 08_ROUTE_INPUT은 02가 정한 domain/scope/target_filter, 06의 counts/requested_job_identifiers/requested_target_status를 기록한다. 08_FINAL_OUTPUT은 최종 route, 선택 작업, routing_reason을 포함한다. 08_TO_NEXT_PAYLOAD는 selected_output/next_node가 포함된 실제 다음 노드 전달값이며 08_MESSAGE_OUTPUT은 사용자 응답이다. 08은 LLM을 호출하지 않으므로 08 LLM 프롬프트 로그는 없다. 캐시된 group output 재호출에서는 판단 로그를 반복하지 않는다.

위 로그의 상세 JSON은 GENERATE_SQL CLOB에서 확인한다. MAP_ID=0, MIG_KIND=WORKFLOW이며, 02/06/08 오류는 ERROR 상태 로그의 MESSAGE에 오류 요약, GENERATE_SQL에 error와 traceback을 기록한다. DB 조회 오류, 대상 미조회, 조회 결과 0건과 정상 NO_RUNNABLE_JOB 응답을 구분한다.
