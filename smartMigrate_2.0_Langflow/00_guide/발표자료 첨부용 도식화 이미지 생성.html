접속. 네 개는 각각 별도 DB가 아니라 설정된 Milvus DB 안의 컬렉션입니다. pymilvus.MilvusClient에 uri, user, password, db_name, timeout을 전달합니다. _milvus_config()가 컴포넌트 입력과 환경변수에서 설정을 모으고 _milvus_client()가 클라이언트를 생성합니다. 실제 비밀번호·키·주소는 장표에 넣지 않았습니다.

동기화. 04_saveVectorDB의 _ensure_collection()이 컬렉션과 인덱스를 준비하고 _sync_collection()이 doc_id/content_hash를 비교해 변경된 활성 문서를 임베딩하여 upsert합니다. sync_all은 RAG와 AS-IS SQL을 동기화하며, Correct SQL 전체를 다시 색인하지 않습니다. Correct SQL 저장 뒤에는 sync_correct_sql로 해당 SQL_SEQ 또는 MAP_ID의 저장 종류만 동기화합니다.

벡터 검색과 조건 조회. _embed_texts() 또는 저장된 벡터를 이용해 dense_vector에 COSINE 검색을 수행하고 필터·Top-K·검색 후 업무 조건을 적용합니다. query()/query_iterator()는 벡터 유사도 순위 없이 메타데이터 조건으로 조회합니다. 장표 코드는 핵심 발췌이며 실제 구현의 output_fields, 추가 필터, 후보 확대·후처리 등은 생략했습니다. 현재 설명한 실행 경로는 dense vector 검색이며 sparse_vector를 이용한 하이브리드 검색이라고 해석하지 않습니다.

General 반영 범위. SQL Conversion/SQL Tuning는 활성 GENERAL 규칙을 category/rule_type 조건으로 조회하고 SOURCE_TABLES 범위를 확인합니다. SOURCE_TABLES가 비어 있으면 공통 적용, 값이 있으면 현재 source table 범위와 겹치는지 확인합니다. 현재 query limit=1000이므로 무조건 모든 General을 제한 없이 넣는다는 의미는 아닙니다.

SM_RAG_RULES. SQL Conversion은 SQL_CONVERSION SEARCH를 query_iterator()로 읽고 SOURCE_TABLES가 겹치는 사례를 모두 사용합니다. Top-K 벡터 검색이 아닙니다. SQL Tuning은 현재 TO_SQL(튜닝 반복 시 현재 SQL)의 MAIN/SUBQUERY 블록을 정규화해 임베딩하고, 가이드 SOURCE_SQL의 정규화 구조+원문으로 생성된 벡터와 COSINE 비교합니다. 후보의 SOURCE_TABLES 적용 범위를 확인한 뒤 블록별 Top-K를 선택합니다. GUIDANCE_TEXT와 TARGET_SQL은 비교 벡터의 대상이 아니라 조회된 결과를 프롬프트에 반영하는 자료입니다. GENERAL 규칙은 두 Executor 모두 category/rule_type 등의 조건 조회와 범위 확인으로 가져옵니다.

SM_ASIS_SQL. 04_ragCommandTool의 _search_similar_asis_sql()이 AS-IS SQL 유사 후보를 검색하고 Oracle의 최신 Conversion 상태와 비교합니다. REF_SEQ 적용은 별도 Update Tool이 담당합니다. SQL Conversion의 _stored_asis_query_vector()는 저장 SQL이 현재 원문과 일치할 때만 벡터를 재사용하고 없거나 불일치하면 새로 임베딩합니다.

SM_CORRECT_SQL_CONVERSION. SQL Conversion의 _correct_sql_hints_text()가 TO_SQL/BIND_SQL/TEST_SQL 생성 힌트를 구성합니다. REF_SEQ가 지정되어 있으면 해당 SQL_SEQ를 조건 조회하여 우선 사용하고, 지정되지 않았으면 원본 SQL 벡터로 유사 Correct SQL을 검색합니다. SQL Tuning이 이 컬렉션을 직접 검색하는 구조는 아닙니다.

SM_CORRECT_SQL_MIGRATION. DB Migration의 _migration_correct_sql_hints()가 테이블·조건·컬럼 매핑 정보를 임베딩하고 현재 생성하는 MIG_SQL 또는 VERIFY_SQL과 같은 종류의 예시를 검색합니다. SQL Formatting은 Milvus를 직접 조회하지 않습니다.

상세 설명

Correct SQL · 상태 변경과 다음 실행

도식은 이 HTML에 포함되어 있습니다. 별도 이미지 파일 없이 확대·축소할 수 있습니다.

Migration. Correct MIG_SQL 저장은 INSERT를 사람이 이미 확인한 의미이며 STATUS=FAIL-TEST, RETRY_COUNT=0이 됩니다. 다음 실행은 INSERT를 반복하지 않고 AI의 VERIFY_SQL 생성과 건수 검증부터 재개하며 이후 시스템이 VERIFY2_SQL을 구성해 레코드 검증을 수행합니다. Correct VERIFY_SQL 저장은 검증까지 사람이 확인한 의미이며 STATUS=PASS, RETRY_COUNT=0으로 Migration을 완료 처리합니다. 초안 저장이나 SQL 저장만으로 이관/검증이 자동 수행된다는 의미가 아닙니다.

Conversion. Correct TO_SQL 저장은 STATUS_CONVERSION=FAIL-BIND이며 다음 실행은 저장 TO_SQL을 재사용해 BIND_SQL 생성·실행으로 BIND_SET을 확보하고 TEST_SQL 생성·검증으로 이어집니다. Correct BIND_SQL은 비어 있지 않은 JSON 객체 배열 BIND_SET과 함께 저장하고 FAIL-TEST로 전이하여 다음 실행에서 TEST_SQL 생성·검증부터 재개합니다. Correct TEST_SQL은 사용자 검증 완료로 PASS-CONVERSION이 되며 후속 Tuning 대상입니다. Tuning에서는 TUNED_TO_SQL과 TUNED_RESULT를 생성합니다.

동기화와 유사 검색. Management Agent는 저장 성공 후 저장한 SQL 한 건·종류를 sync_correct_sql로 동기화하고 Conversion의 AS-IS SQL을 기준으로 유사 실패 작업을 검색합니다. Correct TO_SQL 자체와 후보 TO_SQL을 비교하는 검색이 아닙니다. 동기화나 검색이 실패하면 완료 단계와 실패 단계를 구분하며 참조 등록 성공을 주장하지 않습니다.

후보별 REF_SEQ. 유사도가 엄격히 80%를 초과하고 저장 종류와 후보의 현재 실패 단계가 맞을 때만 적용합니다. TO_SQL→FAIL-TOBE, BIND_SQL→FAIL-BIND, TEST_SQL→FAIL-TEST입니다. 예를 들어 기준 SQL_SEQ=42의 Correct TO_SQL 저장으로 기준 상태는 FAIL-BIND가 되지만 후보는 FAIL-TOBE인 행에 REF_SEQ=42, RETRY_COUNT=0을 적용합니다. 후보의 실패 상태는 유지하고 기준 자신은 제외합니다. 실제 필드명은 REF_SQL이 아니라 REF_SEQ입니다.

별도 실행. REF_SEQ는 저장한 Correct SQL의 SQL_SEQ를 가리킵니다. 후보 SQL 전문을 복사하거나 즉시 실행하지 않고, 이후 명시적인 실행 요청에서 해당 실패 단계의 생성 힌트로 사용합니다. Migration에는 유사 후보 자동 REF_SEQ 적용이 없습니다. 재개 위치는 USER_EDITED 표시가 아니라 DB 상태로 결정합니다.
