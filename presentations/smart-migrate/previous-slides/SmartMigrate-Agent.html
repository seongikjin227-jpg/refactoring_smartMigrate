발표 노트 · 30초 안녕하세요. SQL깍두기 팀입니다. 저는 신입사원으로 SI 개발 프로젝트에 참여하며 노후 플랫폼 리팩토링을 경험했습니다. 그 과정에서 AS-IS SQL을 분석하고 TO-BE 구조에 맞춰 수정하는 반복 작업이 Migration과 개발 업무의 병목으로 느껴졌습니다. 이 경험을 바탕으로 기존 SQL과 매핑룰을 재사용하고 반복 작업을 줄이기 위해 SmartMigrate Agent를 기획했습니다.

발표 노트 · 1분 가장 크게 느낀 병목은 AS-IS SQL을 분석하고 TO-BE SQL로 수정하는 작업의 반복이었습니다. 기존 SQL에 담긴 업무 내용을 이해하고 새 구조에 맞게 바꾸는 일을 계속해야 했습니다. 그래서 기존 SQL을 재활용하고 테이블·컬럼 매핑을 기준으로 변환과 검증을 연결하면 Migration과 개발 업무의 반복을 줄일 수 있겠다고 생각했습니다. SmartMigrate Agent는 이 현장 경험에서 출발한 기획입니다. 개선 효과는 목표이며 아직 측정한 절감률을 뜻하지 않습니다.

발표 노트 · 1분 30초 check_dependency → fetch_ddl → generate → execute → verify → finalize 흐름입니다. 두 SQL은 generate 노드에서 함께 생성됩니다. 검증 SQL 역시 생성물이므로 업무 기준 검토가 필요합니다. 검증 SQL 재생성만으로 정합성이 자동 증명되는 것은 아닙니다.

이관 후, 업무 SQL을 연결합니다.

AS-IS SQL

SELECT e.EMPLOYEE_ID,
       e.FIRST_NAME, e.SALARY
FROM ASIS_HR_EMP e
WHERE e.DEPARTMENT_ID = :dept_id

TO-BE SQL

SELECT e.EMP_ID,
       e.GIVEN_NAME, e.BASE_SALARY
FROM TOBE_HR_EMP e
WHERE e.DEPT_ID = :dept_id

발표 노트 · 1분 30초 원본 Conversion은 SELECT인 경우 바인드가 있으면 최대 3개 사례를 추출해 건수를 비교합니다. non-SELECT는 검증 없이 산출물 생성 후 PASS 저장 경로가 있습니다. 모든 SQL이 실행 검증되는 것은 아닙니다. 튜닝의 건수 검증도 성능 향상 증명은 아닙니다.
