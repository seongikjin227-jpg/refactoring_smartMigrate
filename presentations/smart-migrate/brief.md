# 확정 A · 개발자 발표 브리프

팀 SQL깍두기 / 개발자 청중 / 20~25분 / 데스크톱 스크롤 웹페이지.

## 중심 메시지
테이블과 SQL이 많아지면 작성뿐 아니라 검증 SQL·바인드 조건·결과 대조·재검증의 반복이 병목이 된다. 사람이 업무 흐름과 정합성 기준을 검토해 매핑룰을 확정하면, Agent가 생성·검증 준비·실행·실패 기록을 연결한다. DBA는 실행·검증·실패 분석, B/E 개발자는 매핑과 검토된 TO-BE SQL을 개발에 활용한다.

## 흐름과 시간
| 섹션 | 분 | 핵심 |
|---|---:|---|
| 기획 배경 | 1 | 신입사원 SI 리팩토링 경험 |
| 수백 SQL 검증 부담 | 2 | 인원 조회 예시, 검증 SQL·조건별 테스트·재검증 |
| 사람과 Agent | 1 | 업무 의미·정합성 기준과 반복 처리의 분담 |
| DBA·B/E 활용 | 1 | 사용자별 입력·작업·산출물·후속 판단 |
| 매핑 확정 | 0.5 | 현업 흐름·PK·NULL·중복·검증 기준 |
| 실제 매핑 테이블 | 1.5 | 마스터 2행·상세 10행·SQL 작업 1행 |
| 전체 흐름 | 1 | 매핑 → 이관·검증 → SQL 변환·검증 |
| 전문 Agent 구조 | 2 | Supervisor와 전문 Agent |
| Migration 실행 | 2 | LangGraph 노드·실패·재시도 분기 |

| Dify 시연 | 1 | DB 접근 제약과 JSON 더미 처리 |

총 25분. Dify는 planner의 계획 → execute의 계산 → commit의 검증 → narrator의 해설에 집중한다. JSON 원문·전체 컬럼은 시연 및 질문 대응용 펼쳐보기다.

## 표현 기준
- 매핑 확정은 사람의 활용 기준이며 구현된 승인·권한 시스템을 뜻하지 않는다.
- DBA·B/E는 사용자 구분이며 RBAC나 B/E 코드 자동 반영을 주장하지 않는다.
- 상태·SQL·로그는 원인 분석의 근거이며 자율 진단·복구를 보장하지 않는다.
- 원본 Oracle 처리와 Dify JSON 시연, 목표 INSERT와 현재 MERGE를 구분한다.
- Excel 입출력은 확장 구상이다. 건수 동일성이 의미 동등성·성능 증명은 아니다.
- 핵심 입력 3개를 설명하고 LOG는 자동 업무 이력, RAG는 검색 없는 참고 규칙으로 정리한다. DSL 자체는 수정하지 않는다.
