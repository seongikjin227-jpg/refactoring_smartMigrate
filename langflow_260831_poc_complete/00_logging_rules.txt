# Langflow Workflow Logging Rules

## 0. 현재 결론

첨부 PDF는 Langflow 환경에서 `self.log()`, `lfx.log.logger`, Python `logging`, handler 방식을 테스트한 참고 자료다. 최종 적용은 현재 `langflow_260831_poc_complete` 코드 구조를 기준으로 한다.

현재 결론은 다음과 같다.

- Root Logger는 사용하지 않는다.
- SmartMigrate workflow 로그는 `logging.getLogger("smartmigrate.workflow")` 전용 logger만 사용한다.
- `00A Log Runtime Start`에서 `SmartMigrateDBHandler`를 등록한다.
- `SmartMigrateDBHandler`는 workflow 시작 시 DB connection을 한 번 만들고 보유한다.
- 각 컴포넌트의 `logger.info/error(...)` 호출마다 handler가 같은 connection으로 `SFAADM.NEXT_MIG_LOG`에 즉시 insert한다.
- 이전 방식이었던 batch read/save/Result Table 역할은 제거한다.
- 별도 종료 logging 컴포넌트는 두지 않는다.
- 다음 workflow 시작 시 `00A`가 기존 handler를 제거하고 `handler.close()`를 호출해 이전 DB connection을 닫는다.

## 1. 목적

목적은 Langflow에서 어떤 컴포넌트가 어떤 순서로 실행됐는지 DB에서 확인하는 것이다.

이 runtime logging은 기존 업무 감사 로그를 대체하지 않는다.

- 컴포넌트 이동, 함수 실행, loop item, sleep 전후 확인: `smartmigrate.workflow` logger -> `SmartMigrateDBHandler` -> `NEXT_MIG_LOG`
- SQL 생성/실행/검증/재시도/실패 이력: 기존 `10C` 업무 로그 유지
- SQL 변환/튜닝/포맷팅 상세 이력: 기존 `12C`/`15C`/`17C`의 `NEXT_SQL_LOG` 기록 유지

## 2. Logger 기준

SmartMigrate workflow logging은 전용 logger만 사용한다.

```python
LOGGER_NAME = "smartmigrate.workflow"
logger = logging.getLogger(LOGGER_NAME)
logger.propagate = False
```

아래 Root Logger 패턴은 SmartMigrate workflow logging 수집 용도로 사용하지 않는다.

```python
logging.getLogger()
root_logger = logging.getLogger()
root_logger.addHandler(...)
logging.getLogger().handlers
```

Root Logger에 handler를 붙이면 Langflow 내부 로그(`lfx.custom.validate` 등)까지 섞일 수 있으므로 금지한다.

## 3. 00A Log Runtime Start

`00A_logRuntimeStart.py`는 workflow 시작 시 다음 순서로 처리한다.

1. `logging.getLogger("smartmigrate.workflow")` 획득
2. 해당 logger에 등록된 기존 handler 제거
3. 제거한 handler는 `close()`
4. logger level을 `logging.DEBUG`로 설정
5. `logger.propagate = False`
6. 새 `SmartMigrateDBHandler` 생성
7. DB config는 여기서만 전달
8. logger에 handler 등록
9. workflow start 로그를 즉시 DB insert
10. 입력 payload를 그대로 다음 컴포넌트로 전달

Handler marker는 아래 값으로 고정한다.

```python
HANDLER_MARKER = "SmartMigrateHandler"
```

Handler 검색은 `isinstance()`나 `id(handler)`가 아니라 marker attribute 기준으로 한다.

```python
getattr(handler, "handler_marker", None) == "SmartMigrateHandler"
```

Langflow Custom Component가 reload/recompile되면 같은 클래스명이어도 Python class object가 달라질 수 있으므로 `isinstance()`를 검색 기준으로 쓰지 않는다.

## 4. SmartMigrateDBHandler

`SmartMigrateDBHandler`는 생성 시점에 DB connection을 한 번 만든다.

```python
class SmartMigrateDBHandler(logging.Handler):
    def __init__(self, db_config):
        super().__init__(logging.DEBUG)
        self.handler_marker = "SmartMigrateHandler"
        self.connection = create_db_connection(db_config)
```

`emit()`마다 새 connection을 만들지 않는다. `emit()`에서는 `workflow_log`와 `record.getMessage()`를 읽어 기존 로그 테이블에 insert한다. cursor는 insert 시점마다 생성하고 닫는다.

## 5. Component Logging 형식

각 컴포넌트는 handler를 만들지 않는다. DB connection/input/insert helper도 갖지 않는다.

컴포넌트에서는 전용 logger만 호출한다.

```python
logging.getLogger("smartmigrate.workflow").info("before build_result", extra={"workflow_log": [0, "WORKFLOW", "18D_FULL_WORKFLOW_DASHBOARD", "INFO", "BUILD_RESULT", "START", 0]})
```

`workflow_log` list 순서는 다음과 같다.

```text
map_id, mig_kind, log_type, log_level, step_name, status, retry_count
```

`MESSAGE` 컬럼에는 `logger.info(...)` 또는 `logger.error(...)`의 첫 번째 메시지를 사용한다. 같은 메시지를 `workflow_log` list 안에 중복해서 쓰지 않는다.

## 6. NEXT_MIG_LOG 기준

Runtime workflow log insert 대상 컬럼은 다음이다.

```text
LOG_ID
MAP_ID
MIG_KIND
LOG_TYPE
LOG_LEVEL
STEP_NAME
STATUS
MESSAGE
RETRY_COUNT
CREATED_AT
```

`LOG_ID`는 `MIGRATION_LOG_SEQ.NEXTVAL`을 사용한다.

`UPD_TS`는 사용하지 않는다. Langflow 테스트 DB 기준 `NEXT_MIG_LOG`에는 `CREATED_AT`은 있고 `UPD_TS`는 없다.

Runtime workflow log에서는 `GENERATE_SQL`을 비워 둔다. 생성 SQL이나 실행 SQL은 기존 `10C` 업무 로그에서 기록한다.

## 7. Handler 정리

별도 종료 컴포넌트는 두지 않는다. 다음 workflow 시작 시 `00A_logRuntimeStart.py`가 전용 logger의 기존 handler를 제거하고 `handler.close()`를 호출한다.

```python
logger = logging.getLogger("smartmigrate.workflow")
for handler in list(logger.handlers):
    if getattr(handler, "handler_marker", None) == "SmartMigrateHandler":
        logger.removeHandler(handler)
        handler.close()
```

`handler.close()` 안에서 보유 중인 DB connection도 닫는다. 단일 사용자 테스트 기준에서는 다음 실행 시작 시 이전 connection이 정리되는 방식으로 둔다.

## 8. 기존 업무 로그 유지

아래 코드는 runtime workflow 순서 로그가 아니라 업무 감사 로그이므로 유지한다.

| 컴포넌트 | 기존 기록 대상 | 유지 이유 |
|---|---|---|
| `10C_migOneJobPocExecutor` | `NEXT_MIG_LOG` | migration 단계, retry, 생성/실행 SQL, 실패 이력 |
| `12C_sqlConversionOneJobPocExecutor` | `NEXT_SQL_LOG` | SQL 변환 결과와 단계 메타데이터 |
| `15C_sqlTuningOneJobPocExecutor` | `NEXT_SQL_LOG` | SQL 튜닝 결과와 단계 메타데이터 |
| `17C_sqlFormattingOneJobPocExecutor` | `NEXT_SQL_LOG` | SQL 포맷팅 결과와 단계 메타데이터 |

## 9. 확인 쿼리

```sql
SELECT LOG_ID,
       CREATED_AT,
       MAP_ID,
       MIG_KIND,
       LOG_TYPE,
       LOG_LEVEL,
       STEP_NAME,
       STATUS,
       MESSAGE,
       RETRY_COUNT
  FROM SFAADM.NEXT_MIG_LOG
 WHERE MAP_ID = 0
 ORDER BY LOG_ID;
```
