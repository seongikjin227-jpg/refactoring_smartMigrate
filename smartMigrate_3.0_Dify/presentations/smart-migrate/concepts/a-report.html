현장에서 시작한 문제

SQL 작성·수정 이후에도 검증을 위한 반복 작업이 이어집니다.

신입사원으로 SI 개발 프로젝트에 참여하며 노후 플랫폼 리팩토링을 경험했습니다. AS-IS SQL을 분석하고 TO-BE 구조에 맞게 수정하는 작업이 반복됐고, 바꾼 SQL과 이관 데이터가 올바른지 검증하는 부담도 함께 느꼈습니다.

SQL을 사람이 작성해도 검증 SQL과 테스트 조건을 별도로 준비해야 합니다. 테이블과 SQL이 많아질수록 이 작업을 일일이 관리하기 어려워집니다.

작성 → 검증 SQL → 테스트 → 재검증

확정한 매핑룰과 기존 SQL을 재사용해, 생성부터 검증 준비·반복 실행·실패 추적까지 연결하고자 했습니다.

수백 개 SQL의 검증 부담

검증 SQL 작성과 조건별 실행·비교·재검증까지 자동화의 대상으로 봅니다.

Migration SQL이나 TO-BE SQL을 작성하는 것으로 전환 작업이 끝나지는 않습니다. 이관 데이터가 맞는지, 기존 조회가 같은 업무 결과를 반환하는지 확인할 검증 SQL과 테스트를 다시 만들어야 합니다.

SQL 작성·수정검증 SQL 작성조건·바인드별 실행결과 대조변경 후 재검증
수백 개 SQL × 여러 조건 × 반복 재검증

테이블과 SQL이 많아지면 매핑 변경의 영향, 검증 SQL, 테스트 조건, 실패 목록을 함께 관리해야 합니다. 이 규모 표현은 자동화가 필요한 업무 상황이며, 수백 건 처리 성능을 검증했다는 의미는 아닙니다.

예: 부서별 인원 조회가 같은 결과를 반환해야 합니다.

AS-IS 조회

SELECT e.EMPLOYEE_ID, e.EMAIL
FROM ASIS_HR_EMP e
WHERE e.DEPARTMENT_ID = :dept_id

TO-BE 조회

SELECT e.EMP_ID, e.EMAIL_ADDR
FROM TOBE_HR_EMP e
WHERE e.DEPT_ID = :dept_id
비교 기준무엇이 같아야 할까요?
같은 입력 조건양쪽 모두 같은 dept_id와 동일한 업무 범위를 조회
같은 대상 인원컬럼명을 매핑한 뒤 동일한 직원이 누락·추가 없이 포함
같은 값과 중복이메일 값·NULL·중복 행의 발생 여부를 동일 기준으로 대조
변경 후 재검증매핑·SQL이 바뀌면 관련 작업을 다시 실행하고 실패를 추적

검증 기준을 설명하기 위한 별도 부서 필터 예시입니다. 현재 Dify 시연용 SQL은 뒤에서 소개하는 SQL_SEQ=1 한 개입니다. 위 두 SQL을 Oracle에서 실행한 결과는 아닙니다. 정렬은 업무 요구가 있을 때 별도로 비교합니다.

DBA와 B/E 개발자

하나의 매핑 기준을 서로 다른 업무에 활용합니다.

DBA

실제 Migration과 검증의 반복을 자동화하고, 실패한 작업의 근거를 추적합니다.

  1. 확정 매핑·대상 범위·선행 작업 확인
  2. 이관 SQL·검증 SQL 생성 및 검토
  3. DB 연결 환경에서 이관·검증 실행
  4. 상태·로그·SQL로 실패 원인 분석
  5. 규칙·데이터·SQL 보정 후 재처리

활용 산출물: MIG_SQL, VERIFY_SQL, 작업 상태, 실행 로그

B/E 개발자

매핑룰을 조회하고 생성된 TO-BE SQL을 검토해 새 시스템의 API·업무 로직 개발에 활용합니다.

  1. AS-IS SQL과 테이블·컬럼 매핑 조회
  2. TO-BE SQL 변환 요청
  3. 바인드·조회 조건·결과 의미 확인
  4. 검토한 SQL을 Repository·DAO 등에 적용
  5. API 응답·업무 시나리오 통합 테스트

활용 산출물: 매핑룰, TO_SQL, BIND_SET, 검증 결과

DBA·B/E는 주요 활용 사용자입니다. 두 역할을 구분하는 접근 권한이나 백엔드 코드 자동 반영 기능의 구현을 뜻하지 않습니다.

Agent 사용의 출발점

현업 업무 흐름과 데이터 정합성을 검토해 매핑룰을 확정합니다.

  1. 현업 업무 흐름 파악

    어떤 시점에 데이터가 생성·변경되는지, 누가 어떤 업무에서 조회하는지 이해합니다.

  2. 정합성 기준 정의

    업무 키, 필수값, NULL·중복, 코드 체계, 원천 조건과 검증 범위를 결정합니다.

  3. 매핑룰 확정

    원천 테이블·컬럼과 대상 테이블·컬럼의 대응 및 필요한 변환 기준을 검토합니다.

  4. Agent에 작업 인계

    매핑룰·DDL·기존 SQL을 기준으로 이관과 변환을 요청하고 산출물을 확인합니다.

원본 Oracle 구현에서 BIND_SQL은 바인드가 보존된 TO_SQL의 복사본이 아니라 실제 테스트용 값을 조회하는 SQL입니다. 실행 결과를 BIND_SET으로 저장하고, 최대 3개 바인드 사례의 실제 값을 AS-IS·TO-BE SQL에 대입해 실행 가능한 TEST_SQL을 생성합니다. 미해결 바인드는 남기지 않습니다.

SELECT 검증은 사례별 결과 건수를 비교하며 양쪽 모두 0건인 경우도 실패로 처리합니다. non-SELECT는 실행 검증 없이 SQL 생성 후 PASS를 저장하는 경로가 있습니다. 조회 값 전체의 동등성은 별도로 확인해야 합니다.

[WHERE_ONE] TO_SQL을 입력으로 바깥 WHERE를 WHERE 1 = 1로 시작하도록 통일한다. OR 조건은 괄호로 묶어 의미를 보존한다. 작성 표준이며 성능 개선 주장이 아니다. 이 규칙이 비활성이면 강제로 적용하지 않는다.
대상 원천: ASIS_HR_EMP,ASIS_HR_DEPT

SOURCE_SQL
```sql
SELECT e.EMP_ID FROM TOBE_HR_EMP e WHERE e.DEPT_ID = :dept_id OR e.BASE_SALARY >= :min_salary
```

TARGET_SQL
```sql
SELECT e.EMP_ID FROM TOBE_HR_EMP e WHERE 1 = 1 AND (e.DEPT_ID = :dept_id OR e.BASE_SALARY >= :min_salary)
```

#### RAG_ID 3
[ANSI_JOIN] Oracle (+) 외부 조인을 ANSI LEFT/RIGHT JOIN으로 통일한다. 선택 테이블의 조건 위치와 NULL/중복 행 의미를 보존한다. 예시의 E.DEPT_ID = D.DEPT_ID(+)는 직원 행을 보존하는 LEFT JOIN이다. 불명확하면 변경을 보류하고 사유를 기록한다. Oracle 동등성 검증은 별도다.
대상 원천: ASIS_HR_EMP,ASIS_HR_DEPT

SOURCE_SQL
```sql
SELECT E.EMP_ID, D.DEPT_NAME FROM TOBE_HR_EMP E, TOBE_HR_DEPT D WHERE E.DEPT_ID = D.DEPT_ID(+)
```

TARGET_SQL
```sql
SELECT E.EMP_ID, D.DEPT_NAME FROM TOBE_HR_EMP E LEFT JOIN TOBE_HR_DEPT D ON E.DEPT_ID = D.DEPT_ID
```

#### RAG_ID 4
[REDUCE_SUBQUERY] 같은 테이블의 PK를 IN으로 다시 조회하는 중복 서브쿼리는 PK의 유일성·NOT NULL과 동일 행 조건이 보장될 때 바깥 WHERE 조건으로 축소한다. 예시의 EMP_ID는 TOBE_HR_EMP의 PK다. NULL/중복/집계/행 수 의미가 불명확하면 보류한다. 일반 IN/EXISTS를 JOIN으로 일괄 치환하지 않는다. 근거 없는 인덱스·실행 계획·성능 수치는 제시하지 않는다.
대상 원천: ASIS_HR_EMP,ASIS_HR_DEPT

SOURCE_SQL
```sql
SELECT e.EMP_ID, e.GIVEN_NAME FROM TOBE_HR_EMP e WHERE e.EMP_ID IN (SELECT s.EMP_ID FROM TOBE_HR_EMP s WHERE s.BASE_SALARY >= :min_salary)
```

TARGET_SQL
```sql
SELECT e.EMP_ID, e.GIVEN_NAME FROM TOBE_HR_EMP e WHERE e.BASE_SALARY >= :min_salary
```

(+) → ANSI JOIN과 서브쿼리 축소는 LLM의 조건부 제안입니다. 현재 샘플에 해당 구조가 없으면 미적용 사유를 설명합니다. 복잡한 조인·중첩의 의미 보존과 성능은 Oracle에서 별도로 검증해야 합니다.

복합 요청은 요청한 작업만 순서대로 실행합니다.

SQL 변환 및 튜닝 진행해줘는 actions 목록의 conversion → tuning으로 처리합니다. 로컬 재생에서 TO-BE JSON은 초기 상태로 유지됐고 포매팅도 실행되지 않았습니다. 요청에 없는 이관 계획은 ERROR로 차단합니다.

SQL 변환의 DEMO-GENERATED는 산출물 생성·정적 검사 상태입니다. 현재 Dify의 TEST_SQL은 Oracle 미실행·실제 결과 동등성 미검증을 알리는 문자열이며, 실행 가능한 검증 SQL을 생성·실행한 결과가 아닙니다.

Output · 변경과 오류도 확인합니다.

Dify 컴포넌트의 책임

메인 Chatflow와 내부 Workflow Tool의 입력·출력·검증 경계를 분리합니다.

원본의 전문 Agent 구조를 Dify에서는 기본 Agent와 통합 Workflow Tool 하나로 재현했습니다. LLM은 요청 해석·계획·해설을, Code는 실행·비교·상태 검사를 맡습니다.

메인 Chatflow · 대화와 상태 관리

  1. Startstart

    초기 테이블 JSON과 대화 요청

    최초 샘플 입력과 후속 대화의 진입점입니다.

    전달 값 선택 입력과 현재 사용자 요청

  2. Codeinitialize

    저장된 상태 또는 샘플을 복원

    최신 테이블을 준비합니다. Agent가 상태 전체를 새로 만들게 하지 않습니다.

    전달 값 state_json · session_transport · request_id

  3. Agentagent

    사용자 요청을 통합 Workflow Tool로 전달

    request는 모델이 작성하고 상태는 initialize 출력에서 연결합니다. 실제 작업 계획과 실행은 Tool 내부가 담당합니다.

    전달 값 request + 사전 연결된 session_json

  4. Codecommit

    Tool 응답을 검증하고 반영할 상태를 확정

    요청 ID·입력 해시·revision을 비교합니다. Agent의 자연어 답변을 상태의 근거로 사용하지 않습니다.

    전달 값 state_json · answer · commit_status · narrative_json

  5. Variable Assignersave

    확정한 상태를 대화 변수에 저장

    같은 대화에서 변경을 이어갑니다. 대화 간 공유 DB나 영구 업무 저장소를 뜻하지 않습니다.

    전달 값 다음 턴에서 복원할 상태

  6. LLMnarrator

    검증된 요약으로 결과 해설과 다음 작업 안내

    상태를 변경하거나 DB 실행 결과를 만들어내는 노드가 아닙니다.

    전달 값 한국어 설명

  7. Answeranswer

    해설과 확정 상태의 결과 표 출력

    표와 처리 상태는 commit이 확인한 사실을 기준으로 전달합니다.

    전달 값 사용자에게 보이는 설명 + 표

Agent → Workflow Tool 호출 → Agent Tool 응답 → commit

Tool은 Agent가 호출하는 내부 실행 경로입니다. 메인 그래프에서 Agent와 commit 사이에 독립적인 직렬 노드가 추가되는 구조는 아닙니다.

통합 Workflow Tool · 계획과 실행

  1. Startstart

    Tool 인자 수신

    Agent에서 호출한 요청과 사전 연결한 최신 상태를 받습니다.

    전달 값 request · session_json

  2. Codeprepare

    상태 검증과 계획용 문맥 구성

    현재 매핑·SQL·참고 규칙과 대화 문맥을 정리합니다.

    전달 값 state_json · context_json · request · request_id

  3. LLMplanner

    요청을 구조화된 작업 계획·SQL로 변환

    query·insert·update·delete·run·clarify·export 중 지원 작업을 계획합니다. 모호한 요청은 clarify로 남깁니다.

    전달 값 action · stage · 대상 키 · SQL 산출물

  4. Codeexecute

    계획 검사 후 JSON 작업·검증 수행

    허용된 작업을 실행합니다. 이관은 PK 기준 추가·갱신과 COUNT·행 값 비교를 수행하며 임의 SQL을 DB에서 실행하지 않습니다.

    전달 값 result_json

  5. Endend

    작업 결과를 Agent로 반환

    반환된 결과는 메인 commit의 검증을 통과한 뒤 대화 상태에 반영됩니다.

    전달 값 result_json

왜 계획 LLM과 실행 Code를 나누었을까요?

계획은 생성형 모델이 만들지만, 실제 변경은 허용 작업·키·매핑·SQL 산출물 검사를 거칩니다. Code가 계산한 결과와 상태를 확정한 뒤 LLM이 설명하게 해, 자연어 응답과 실제 작업 결과를 구분합니다.

Tool 결과 계약과 commit 검증
{
  "kind": "smartmigrate.result.v1",
  "request_id": "이번 요청 ID",
  "base_hash": "입력 상태 SHA-256",
  "base_revision": 0,
  "status": "OK | ERROR | NEEDS_INPUT",
  "state_json": "변경된 상태 JSON 문자열",
  "answer": "처리 결과"
}

commit은 Tool 응답에서 결과를 읽어 request_id, base_hash, base_revision과 반환 상태 revision을 확인합니다. 중복된 동일 결과는 하나로 보고, 서로 다른 결과는 CONFLICT로 거부합니다. 결과가 없으면 NO_RESULT로 원래 상태를 유지합니다. 해시는 오래된 상태 확인용이며 인증 수단이 아닙니다.

현재 commit Code의 최상위 출력은 DSL 선언과 맞춘 문자열 4개(state_json, answer, commit_status, narrative_json)입니다.

저장소의 Dify 1.15 대상 DSL 01·02와 노드 소스를 기준으로 정리했습니다. 설치 서버의 실제 import·모델 호출 성공을 새로 검증한 결과는 아닙니다.

실패에서 다음 조치까지

상태·로그·SQL·검증 결과를 DBA의 원인 분석 근거로 연결합니다.

DBA는 실패 상태와 로그를 시작점으로, 문제가 매핑·SQL·데이터·실행 환경 중 어디에 있는지 좁힐 수 있습니다. 원인 후보와 조치 판단을 연결하는 활용 방식입니다.

실패 지점확인할 근거사람이 판단할 다음 조치
선행 작업PRIOR_MAP_ID, 선행 작업 상태선행 작업 복구 후 후속 실행 여부 결정
SQL 실행MIG_SQL, 오류 메시지, DDL·제약조건SQL·매핑·권한·데이터 중 원인 후보 확인
검증VERIFY_SQL, 불일치 건수·행, 매핑 기준잘못된 데이터와 잘못된 검증 기준을 구분
Dify 상태 반영commit_status, request_id·hash·revision결과 누락·충돌·오래된 상태 여부 확인
분석 근거를 모으는 자동화와 원인 확정은 구분합니다.

현재 구현은 상태·SQL·검증 결과·로그를 제공합니다. 모든 실패를 AI가 자율적으로 진단·복구한다고 보장하지 않습니다. 재시도만 반복하기보다 매핑과 검증 기준을 함께 확인해야 합니다.

Dify 시연에서 실패가 상태를 바꾸지 않게 하는 방식

잘못된 계획 JSON, 누락된 SQL 산출물 등 실행 실패는 업무 변경을 취소하고 오류 결과를 반환합니다. commit은 결과 없음·충돌·손상·오래된 상태를 거부하거나 원래 상태를 보존합니다. LLM 호출 자체의 오류는 Dify 실패 노드와 Traceback을 확인해야 합니다. 원본 Oracle 트랜잭션 동작과 이 JSON 시연의 롤백을 동일한 보장으로 설명하지 않습니다.
